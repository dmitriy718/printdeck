## Review mandate

This is a new comprehensive review of the complete first-party PrintDeck
repository, followed by a market/user-demand research and recommendation pass.
The engineering review covers architecture, correctness, security, safety,
reliability, concurrency, memory/resource ownership, performance,
maintainability, UI truthfulness, network and printer protocols, build/release
configuration, tests, scripts, and documentation consistency.

Every finding will be classified and recorded. Issues that can be corrected
safely from repository evidence will be fixed and validated. Hardware-dependent,
destructive, credential-affecting, printer-command, eFuse, SD-format, and public
repository operations will not be inferred from this mandate.

The research pass will gather demand signals from multiple source classes,
define a reproducible scoring model for credibility, user value, company value,
profit potential, feasibility, risk, and scalability, then produce seven ranked
recommendations in this review and in `Reviews/recommendations.md`.

## Findings register

| ID | Severity | Area | Finding | Status |
| --- | --- | --- | --- | --- |
| R29-001 | High | Printer concurrency | `stop_mqtt()` freed the shared report-fragment buffer before the MQTT event task was stopped. A late `MQTT_EVENT_DATA` callback could write through freed memory during profile replacement or shutdown. | **Fixed in v0.7.3 source.** Stop/destroy now completes before the worker releases the buffer; invariant added. |
| R29-002 | High | Printer command safety | Pause/resume/cancel were checked before entering the worker queue but not when dispatched. A job-state transition while the command waited could send a stale destructive/control command. | **Fixed in v0.7.3 source.** One shared predicate now gates the UI-facing check, enqueue path, and actual dispatch against the latest atomic state. |
| R29-003 | Medium | UI truthfulness | The footer reported `Accepted` when only the local FreeRTOS queue had accepted a command; no printer acknowledgment had been observed. | **Fixed.** The immediate result is now `Command queued`. A true asynchronous acknowledgment model remains recommendation 6. |
| R29-004 | Medium | OTA target safety | Python's `ipaddress.is_private` includes some reserved/documentation ranges, so the uploader's implementation was broader than its promised “private IPv4” boundary. | **Fixed.** Only explicit RFC 1918 networks are accepted; a 12-address boundary matrix and repository invariant pass. |
| R29-005 | Low | Security documentation | The public camera header said its NVS LAN profile was encrypted even though credentials are deliberately plaintext at rest pending an eFuse provisioning decision. | **Fixed.** The comment now says local-LAN profile and matches the security documentation. |
| R29-006 | Low | Release documentation | The README still listed a future wired partition-table update even though the 512 KiB coredump layout was installed and runtime-verified in v0.7.1/v0.7.2. | **Fixed.** Roadmap and source/deployed version distinction now match the evidence. |
| R29-007 | Medium | Event reliability | Wi-Fi driver/retry and printer profile callbacks use zero-wait queue sends and can drop events under saturation. The error is logged, but a dropped validation event can delay persistence and a dropped driver event can temporarily stale state. No saturation failure has been observed. | **Open architectural risk.** A robust correction needs reserved event capacity, queue sets, or idempotent pending-event flags and hardware reconnect-storm tests; blocking the ESP/MQTT event tasks was not introduced without those tests. |
| R29-008 | High | Credential storage | Wi-Fi and P1S access credentials remain plaintext in NVS. | **Open owner/provisioning decision.** Real protection requires an irreversible HMAC/flash-encryption eFuse and recovery-path decision documented in `docs/SECURITY_PROVISIONING.md`; no eFuse action is authorized by this review. |
| R29-009 | Medium | Wi-Fi coprocessor | The installed ESP32-C6 firmware reports 2.3.0 while the host component is 2.11.7 and warns about possible RPC timeouts. | **Open hardware migration risk.** Wi-Fi is operational; changing the sole network coprocessor without a proven rollback/recovery procedure would be riskier than retaining the known state. |
| R29-010 | High | Power integrity | The prior hardware record contains one genuine brownout at the Wi-Fi/P1S load transition, followed by stable boots but no inline voltage/current diagnosis. | **Open physical finding.** Source cannot establish whether the cable, hub, regulator, or transient load caused it. |
| R29-011 | Medium | Test coverage | Parser, invariants, analyzers, signed builds, and short hardware samples exist, but there is no UI simulator, queue-saturation suite, hardware-in-the-loop harness, or complete v0.7.3 regression. | **Open validation work.** v0.7.3 is not labeled deployed or hardware-verified. |
| R29-012 | Low | NVS recovery policy | `init_nvs()` follows the ESP-IDF template and erases the whole NVS partition on `NO_FREE_PAGES` or `NEW_VERSION_FOUND`, which can remove saved profiles. | **Open product-policy decision.** Removing the recovery erase can make the controller permanently unable to initialize NVS; a safe fix requires an explicit recovery UI/export/re-entry design. |
